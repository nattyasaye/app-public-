### Migration & Hardening Chain (`AppDatabase.onUpgrade`)
- **Fail-Closed Downgrade Guard (`from > to`) & `schemaVersion => 8`:** Because Drift's `MigrationStrategy` has no `onDowngrade` callback and routes `from > to` opens into `onUpgrade(m, from, to)`, the top of `onUpgrade` immediately throws `UnsupportedDatabaseVersionException(fromVersion: from, toVersion: to)` before any `from < N` step or index statement runs. Because Drift (`NativeDatabase`) does not automatically wrap `onUpgrade` in a SQLite transaction, `AppDatabase.migration` explicitly wraps `onUpgrade` execution inside `transaction(() async { ... })` via `_withTransactionalUpgrade` (after the fail-closed `from > to` guard) so any failure rolls back all DDL and DML atomically.
- `from < 2`: Creates double-entry tables (`AccountsTable`, `PartiesTable`, `JournalEntriesTable`, `PostingsTable`, `DebtsTable`, `SettlementAllocationsTable`).
- `from < 3`: Adds `openingBalanceCents` and `openingBalanceDate` to `AccountsTable`.
- `from < 4`: Adds rich task/note fields, `isArchived` on categories, transaction transfer/correction columns, and `CalendarEvents`.
- `from < 5`: Pre-flight validates legacy dates (`_validateLegacyDatesBeforeV5Migration` fail-closed), adds `endDateIso`, and converts `DateTimeColumn` civil dates to canonical `YYYY-MM-DD` strings in `UTC+3`.
- `from < 6` / `< 7`: `V6LedgerMigrator` + `V7LedgerHardener` normalize account `subType` & `isSystem`, synthesize `SYSTEM_CONTROL_ACCOUNT_IDS`, link debt write-offs, backfill `CommitmentSettlementsTable`, verify 5-case opening balances, audit Tier A/B debt controls, and run `verifyInvariantsOnly(db)`—rolling back atomically on failure.
- `from < 8`: Additive, idempotent reminder fidelity upgrade adding nullable `reminders.title` and `reminders.channel_id` via `_addColumnIfMissing` and running `PRAGMA foreign_key_check` prior to commit, preserving all pre-existing reminder rows with `null` values for the new columns.
- `beforeOpen`: Enables `PRAGMA foreign_keys = ON` after the migration transaction commits. (Because SQLite treats `PRAGMA foreign_keys` toggles inside an active transaction as a no-op, pre-commit relational checks inside `onUpgrade` MUST execute `PRAGMA foreign_key_check` explicitly.)

## 3. Financial & Calendar Data Invariants

### Finance Invariants (**Partially implemented** — Recovery Stage 2.1 **Implemented** / Conditionally Accepted; Stage 2.2 ETB Isolation **Implemented in Code; Android CI Pending**)
- **Integer Minor Units (Stage 2.1 — Implemented / Conditionally Accepted)**: `1 ETB = 100 cents`. Zero floating-point amounts in ledger design and core domain rules.
- **Balanced Postings & System Control Accounts (`SYSTEM_CONTROL_ACCOUNT_IDS`)**: Every `JournalEntry` requires $\sum \text{Debits} == \sum \text{Credits}$ and strictly positive `amountCents`; system control IDs (`acc-sys-equity`, `acc-sys-income`, `acc-sys-expense`, `acc-sys-receivable`, `acc-sys-payable`, `acc-sys-legacy-offset`) are excluded from user account totals.
- **Immutable History**: Transactions/journal entries use `isVoided` / `isSuperseded` + `correctedFromEntryId` / `voidReason` instead of destructive history rewriting.
- **Finance v7 Ledger Integration Status**: Existing Finance v7 architecture is **Partially implemented**, with identified defects and incomplete cross-platform integration between Flutter SQLite and Web Preview (`localStorage` / `SharedStateBridge`).
- **Stage 2.2 Strict ETB Currency Isolation ([ADR-003](./decisions/ADR-003-finance-v7-double-entry-and-etb-isolation.md)):** Accounts classify deterministically via `classifyCurrencyCode` as `verified_etb`, `verified_non_etb`, or `unverified`. All new account creations, ledger writes, transfers, commitments, savings goals, recurring rules, quick-capture triage, `SharedFoundationBridge.auditConsistency`, and fail-closed `unvoidJournalEntry`/`restoreTransaction` activations enforce verified ETB only; legacy unverified accounts remain isolated/read-only (rename/archive only); non-ETB and unverified persisted records remain strictly excluded from ETB Safe Harbor, Net Worth, P&L, Cashflow, and debt totals while displaying explicit `Excluded (<CODE>)` / `Currency Review` / `(Unverified)` indicators without reinterpreting unknown amounts as ETB. Strict integer minor-unit decimal parsing eliminates floating-point input math on both platforms. Web/Node Stage 2.2 enforcement is verified via `npm test`; Flutter/Drift execution remains **Unverified** locally pending CI (`flutter analyze` & `flutter test`).

### Calendar & Time Invariants (**Implemented** in Dart & TypeScript)
- **Zone**: Fixed `Africa/Addis_Ababa` (`UTC+3`, `fixedUtcOffsetMinutes: 180`, zero DST).
- **Date-Only vs. Instant**: Civil calendar dates use `YYYY-MM-DD` (`CalendarDate`); timestamps use UTC ISO-8601 (`EthiopiaClock`).
- **Ethiopian Calendar**: 13 months; 30 days in months 1–12; Pagume 5 days (6 in leap years where `year % 4 == 3`); Julian Day Number anchor `1724221`.

## 6. Backward Compatibility & Versioning Rules ([ADR-007](./decisions/ADR-007-mandatory-backward-compatibility.md))

All new schema, persisted-model, backup, snapshot, and import/export changes MUST comply with Constitution Section 2.11 and [ADR-007](./decisions/ADR-007-mandatory-backward-compatibility.md):

1. **Preserve Previously Released Migrations & Backups:** Previously released `AppDatabase.onUpgrade` steps (`from < 2` through `from < 8`, verified sequentially ascending in `app_database.dart`) and previously released `.daywell` backup formats (`format_version: 1`) remain supported until retired by an explicit, approved deprecation decision (no arbitrary rolling cutoff). Static AST/token enforcement via `npm run check-migrations` ([`scripts/check_migration_compatibility.mjs`](../../scripts/check_migration_compatibility.mjs) and [`scripts/migration_compatibility_baseline.json`](../../scripts/migration_compatibility_baseline.json)) extracts the active `MigrationStrategy get migration` getter body, verifies monotonic `schemaVersion >= 8`, explicit `if (from > to) { throw ...; }` fail-closed guard at the top of `onUpgrade` (and absence of nonexistent Drift `onDowngrade`), preserved ascending `from < 2..8` branches and sequential future `from < N` steps, required delegate classes (`V6LedgerMigrator`, `V7LedgerHardener`), and prohibition of `fallbackToDestructiveMigration` (**runtime SQLite migration execution remains CI/Flutter-only and Unverified locally**).
2. **Forward Database Migration Standards (`v8` Baseline -> `v9+`):**
   - `AppDatabase.schemaVersion => 8` is the current production baseline from which all future schema increments (`v9+`) must guarantee non-destructive upgrades and user data preservation.
   - All future `onUpgrade` steps (`from < 9`, ...) must remain incremental (`if (from < N)` in ascending order), deterministic, idempotent when reopened at the target `user_version`, and free of destructive table drops or data resets.
   - New columns added to existing tables must either be nullable or specify safe deterministic defaults/backfills.
   - Pre-flight data/invariant checks run inside the `onUpgrade` migration transaction before irreversible mutations; relational integrity is checked pre-commit via `PRAGMA foreign_key_check` (because SQLite ignores `PRAGMA foreign_keys` changes mid-transaction) and enforced post-commit via `beforeOpen` (`PRAGMA foreign_keys = ON`).
   - Failed migrations must roll back atomically leaving the prior `PRAGMA user_version`, schema, and user rows intact; unsupported future schemas (`from > to`) must fail closed with `UnsupportedDatabaseVersionException` / `DatabaseFailureCategory.unsupportedSchemaVersion` without deleting or overwriting user database files or allowing blind retries.
3. **Deterministic Upcasting, Separate Version Domains & Fail-Closed Future Versions (Stage 3.4.2 / 3.4.4.1):** Supported prior snapshot/import formats MUST remain distinct across version domains and fail safely before any destructive mutation when unsupported:
   - **Flutter Canonical Snapshots (`DatabasePersistenceCoordinator`):** Exports `schemaVersion: 8`; accepts canonical integer versions `4..8` (preserving legacy omitted-version default `5` strictly when neither `schemaVersion` nor `version` key is present); rejects `0..3`, negative/non-integer/null/contradictory versions, future versions (`> 8`), Drift length overflows, non-positive amounts, missing `v7+` transfer `categoryId`, explicit non-ETB/unrecognized/blank account `currencyCode`, and omitted `v7+` account `currencyCode` (preserving omitted pre-v7 legacy `currencyCode` as unverified `''` with `CURRENCY_UNVERIFIED_ON_LEGACY_IMPORT` diagnostic) *before* closing or mutating SQLite, preserving all 22 tables including `Reminders` and `AppSettings`.
   - **Web `SharedStateBridge`:** Continues emitting canonical exchange `schemaVersion: 5` alongside `financeSchemaVersion: 7`; `importFromAndroidJson` accepts canonical exchange/Android snapshot `schemaVersion` `4..8` (or omitted legacy default `5`) paired with optional `financeSchemaVersion: 7` (preserving Reminder `title`/`channelId` and `milestones` validation across `Android v8 <-> Web <-> Android v8` round trips), rejects legacy `LocalDatabaseState` v3 (`version: 3`), versions `< 4`, future canonical versions (`> 8`), invalid/future `financeSchemaVersion` (`!= 7`), Drift max-length overflows, non-positive amounts, missing `v7+` transfer `categoryId`, explicit non-ETB/unrecognized/blank account `currencyCode`, and omitted `v7+` account `currencyCode` (preserving omitted pre-v7 legacy `currencyCode` as unverified `''` rather than coercing `'ETB'`) *before* modifying any `localStorage` key.
   - **Encrypted `.daywell` Backups (`EncryptionBackupService` & `backupCrypto.ts`):** Validates `format`, `format_version: 1`, `kdf: 'PBKDF2-HMAC-SHA256'`, exact `iterations: 100000`, Base64 lengths, and `checksum_sha256` before decryption or quarantine. Both verify AES-GCM authentication first (`authenticationFailure` with neutral guidance on empty passphrase, wrong passphrase, or tampered ciphertext/MAC), then verify `checksum_sha256` against decrypted raw plaintext bytes (`integrityFailure`), then decode strict UTF-8 and JSON (`invalidPayload`). Flutter resolves omitted inner `schemaVersion`/`version` to legacy `5` (canonical bounds `4..8`) and enforces `effectiveInnerVersion == header.schema_version` (`invalidSnapshotVersion` on mismatch) before DB close, quarantine, or mutation; Web `decryptDatabaseBackup` enforces explicit `LocalDatabaseState` `version: 3` matching `header.schema_version: 3` (no omitted-version default). Semantic failure kinds: `authenticationFailure`, `invalidBackupHeader`, `unsupportedFormatVersion`, `unsupportedKdf`, `unsupportedFutureSchema`, `invalidSnapshotVersion`, `invalidPayload`, `integrityFailure`, `databaseImportFailure`. *(Exchange/seed schemaVersion alignment vs. Android runtime `schemaVersion: 8` remains intentionally separated across version domains.)*
4. **No Blanket Historical Rewrite:** Existing historical migrations (`from < 2` through `from < 8`) and untouched historical defects are evaluated on touch or when posing material data-integrity or functionality risks rather than through unrequested blanket retroactive rewrites.
