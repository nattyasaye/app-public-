### Projects Stage 1 Data & Calculation Invariants (**Implemented** — Web Node-verified; Flutter CI-pending)

- **Projects vs. Tasks Distinction:** Ordinary **Tasks** remain single actionable items managed in `TasksController` / `DriftTasksRepository`, optionally associating to a Project via `Tasks.projectId`. **Projects** are independent user-created initiatives representing structured outcomes, milestones, custom metadata definitions/values (`customFieldsJson`), and reusable tracking blocks managed through `IProjectsRepository` (`DriftProjectsRepository` / `WebProjectsRepository`) and `ProjectsController`.
- **Three-Table Relational Model:**
  1. `Projects`: Keeps `id`, `goalId`, `title`, `description`, `status` (`active | completed | on_hold`), `targetDate`, `createdAt` and adds `isArchived` (orthogonal lifecycle flag preserving `status`), optional `startDate` (`YYYY-MM-DD`), typed `customFieldsJson` (`definitions`, `values`, `primaryBlockId`), and `updatedAt`.
  2. `ProjectTrackingBlocks`: Per-project reusable typed blocks (`counter`, `grouped_list`, `checklist`, `schedule`) with `unitLabel`, optional `targetValue`, optional `dailyTargetValue`, `sortOrder`, `isArchived`, and typed `configJson` (no arbitrary formulas/scripts). Max `32` blocks per project.
  3. `ProjectTrackingRecords`: Unified records (`group`, `grouped_item`, `checklist_item`, `schedule_item`, `progress_log`) with `parentRecordId`, optional `linkedTaskId`, `targetValue`, `deltaValue`, `durationMinutes`, `isCompleted`/`completedAt`, canonical `recordedDate`/`scheduledDate` (`YYYY-MM-DD`), and bounded `metadataJson`.
- **Ownership, Hierarchy, Deletion & Append-Only History:**
  - Validation rejects cross-project block references, cross-block/missing parent records, invalid record-to-block pairings, parent cycles, nesting deeper than `3`, direct logging on rollup counters (`rollupSourceBlockId != null`), checklist progress logs, missing `goalId`/`linkedTaskId` on writes, and negative `progress_log` deltas without explicit correction metadata.
  - `progress_log` rows are append-only: `updateRecord` and `deleteRecord` fail closed; corrections must append a compensating `progress_log` (`metadata.isCorrection = true`, `compensatesRecordId`, `correctionReason`) via `appendProgressCorrection`.
  - Archiving a project or block never destroys historical records. Deleting a block or project cascades only owned tracking blocks/records/milestones bottom-up while detaching `Tasks.projectId` to `null` (`Tasks` survive intact).
- **Deterministic Progress & Duration Rules:**
  - `ProgressEngine` / `projectsEngine.ts` treat project definitions (`targetValue`, planned `durationMinutes`, `customFields`) as distinct from derived rollups (`loggedTotal`, `groupMetrics`, `dailyTotalsByDate`, `actualLoggedDurationMinutes`), maintaining one source of truth when a counter rolls up from a `grouped_list` via `rollupSourceBlockId`.
  - Multiple independent measurements (counter/grouped items, checklist completion, schedule completion, planned vs. actual watched minutes, linked tasks excluding `cancelled`, milestones) are never implicitly averaged; `overallPercentage` is populated **only** when `customFields.primaryBlockId` references an existing non-archived block.
  - For video/curriculum schedules, `durationMinutes` stores planned length, `progress_log.deltaValue` records actual watched minutes without conflating completion with watched time, and `ScheduleBlockConfig.completionRule` evaluates `manual`, `threshold_percent`, or `exact_duration` explicitly via `meetsScheduleDurationRule`.

### Migration & Hardening Chain (`AppDatabase.onUpgrade`)
- **Fail-Closed Downgrade Guard (`from > to`) & `schemaVersion => 13`:** Because Drift's `MigrationStrategy` has no `onDowngrade` callback and routes `from > to` opens into `onUpgrade(m, from, to)`, the top of `onUpgrade` immediately throws `UnsupportedDatabaseVersionException(fromVersion: from, toVersion: to)` before any `from < N` step or index statement runs. Because Drift (`NativeDatabase`) does not automatically wrap `onUpgrade` in a SQLite transaction, `AppDatabase.migration` explicitly wraps `onUpgrade` execution inside `transaction(() async { ... })` via `_withTransactionalUpgrade` (after the fail-closed `from > to` guard) so any failure rolls back all DDL and DML atomically.
- `from < 2`: Creates double-entry tables (`AccountsTable`, `PartiesTable`, `JournalEntriesTable`, `PostingsTable`, `DebtsTable`, `SettlementAllocationsTable`).
- `from < 3`: Idempotently adds `openingBalanceCents` and `openingBalanceDate` to `AccountsTable` via `_addColumnIfMissing` (safe when `from < 2` just created `AccountsTable` with current columns during `v1 -> v13` upgrades).
- `from < 4`: Adds rich task/note fields, `isArchived` on categories, transaction transfer/correction columns, and `CalendarEvents`.
- `from < 5`: Pre-flight validates legacy dates (`_validateLegacyDatesBeforeV5Migration` fail-closed), adds `endDateIso`, converts `DateTimeColumn` civil dates to canonical `YYYY-MM-DD` strings in `UTC+3`, and migrates `tasks` (with `_existingTableColumns('tasks')`, `newColumns`, and defaults `isArchived: false`, `sortOrder: 0` for `< v5` upgrades) and `projects` (safe column defaults `isArchived: false`, `customFieldsJson: '{}'`, `updatedAt: createdAt`) via `TableMigration`.
- `from < 6` / `< 7`: `V6LedgerMigrator` + `V7LedgerHardener` normalize account `subType` & `isSystem`, synthesize `SYSTEM_CONTROL_ACCOUNT_IDS`, link debt write-offs, backfill `CommitmentSettlementsTable`, verify 5-case opening balances, audit Tier A/B debt controls, and run `verifyInvariantsOnly(db)`—rolling back atomically on failure.
- `from < 8`: Additive, idempotent reminder fidelity upgrade adding nullable `reminders.title` and `reminders.channel_id` via `_addColumnIfMissing` and running `PRAGMA foreign_key_check` prior to commit, preserving all pre-existing reminder rows with `null` values for the new columns.
- `from < 9`: Additive, idempotent Projects Stage 1 upgrade adding `projects.{is_archived, start_date, custom_fields_json, updated_at}`, backfilling `updated_at = created_at` on pre-existing rows without mutating Tasks/Milestones/Notes/Finance data, creating `project_tracking_blocks`, `project_tracking_records`, and 5 v9 query indices (`idx_project_blocks_project_sort`, `idx_project_records_project_block`, `idx_project_records_parent`, `idx_project_records_recorded_date`, `idx_project_records_linked_task`), and running `PRAGMA foreign_key_check` prior to commit.
- `from < 10`: Additive, idempotent Stage 0.2B Tasks & Daily Planning upgrade adding `tasks.{completed_at, scheduled_time, my_day_date, recurrence_config_json, is_archived DEFAULT 0, sort_order DEFAULT 0}` via `_addColumnIfMissing`, creating `daily_planning_entries` via `_createTableIfMissing` (with `task_id -> tasks(id) ON DELETE CASCADE`), creating 4 v10 query/uniqueness indices (`idx_daily_planning_task_date` unique on `(task_id, plan_date)`, `idx_daily_planning_plan_date`, `idx_tasks_my_day_date`, `idx_tasks_archived_sort`), and running `PRAGMA foreign_key_check` prior to commit. **Stage 0.2C** adds `DriftTasksRepository` / `TasksController` CRUD + `SharedStateBridge` / `DatabasePersistenceCoordinator` v10 serialization and snapshot compatibility.
- `from < 11`: Additive, idempotent Stage 8 Note Task-Link upgrade adding nullable `notes.linked_module` and `notes.linked_id` via `_addColumnIfMissing`, creating `idx_notes_linked` on `(linked_module, linked_id)` via `_createV11NotePerformanceIndices()`, and running `PRAGMA foreign_key_check` prior to commit, preserving all pre-existing notes and `projectId`/`goalId` links.
- `from < 12`: Additive, idempotent Stage B Daily Rhythm upgrade creating `daily_rhythm_days` (`date_iso` PK) via `_createTableIfMissing('daily_rhythm_days', () => m.createTable(dailyRhythmDays))`, creating `idx_daily_rhythm_days_updated_at` via `_createV12DailyRhythmPerformanceIndices()`, and running `PRAGMA foreign_key_check` prior to commit with zero fabricated historical check-ins and full preservation of all v1–v11 rows.
- `from < 13`: Additive, idempotent Stage 5 Finance SMS Drafts upgrade creating `sms_drafts_table` via `_createTableIfMissing('sms_drafts_table', () => m.createTable(smsDraftsTable))`, creating deduplication/review indices (`idx_sms_drafts_fingerprint`, `idx_sms_drafts_provider_ref`, `idx_sms_drafts_status_received`) via `_createV13SmsDraftPerformanceIndices()`, and running `PRAGMA foreign_key_check` prior to commit while leaving all v1–v12 tables and ledger balances untouched. (`app_database.g.dart` regeneration via `dart run build_runner` and Flutter SQLite runtime test execution await CI.)
- `beforeOpen`: Enables `PRAGMA foreign_keys = ON` after the migration transaction commits. (Because SQLite ignores `PRAGMA foreign_keys` toggles inside an active transaction as a no-op, pre-commit relational checks inside `onUpgrade` MUST execute `PRAGMA foreign_key_check` explicitly.)

## 3. Financial & Calendar Data Invariants

### Finance Invariants (**Partially implemented** — Recovery Stage 2.1 **Implemented** / Conditionally Accepted; Stage 2.2 ETB Isolation **Implemented in Code; Android CI Pending**)
- **Integer Minor Units (Stage 2.1 — Implemented / Conditionally Accepted)**: `1 ETB = 100 cents`. Zero floating-point amounts in ledger design and core domain rules.
- **Balanced Postings & System Control Accounts (`SYSTEM_CONTROL_ACCOUNT_IDS`)**: Every `JournalEntry` requires $\sum \text{Debits} == \sum \text{Credits}$ and strictly positive `amountCents`; system control IDs (`acc-sys-equity`, `acc-sys-income`, `acc-sys-expense`, `acc-sys-receivable`, `acc-sys-payable`, `acc-sys-legacy-offset`) are excluded from user account totals.
- **Immutable History**: Transactions/journal entries use `isVoided` / `isSuperseded` + `correctedFromEntryId` / `voidReason` instead of destructive history rewriting.
- **Finance v7 Ledger Integration Status**: Existing Finance v7 architecture is **Partially implemented**, with identified defects and incomplete cross-platform integration between Flutter SQLite and Web Preview (`localStorage` / `SharedStateBridge`).
- **Stage 2.2 Strict ETB Currency Isolation & Finance Stage A Snapshot Compatibility ([ADR-003](./decisions/ADR-003-finance-v7-double-entry-and-etb-isolation.md)):**
  - **Runtime ETB Isolation:** Accounts classify deterministically via `classifyCurrencyCode` as `verified_etb`, `verified_non_etb`, or `unverified`. All new account creations, ledger writes, transfers, commitments, savings goals, recurring rules, quick-capture triage, `SharedFoundationBridge.auditConsistency`, and fail-closed `unvoidJournalEntry`/`restoreTransaction` activations enforce verified ETB only; legacy non-ETB and unverified accounts remain isolated/read-only (rename/archive only) and strictly excluded from ETB Safe Harbor, Net Worth, P&L, Cashflow, and debt totals without FX conversion or reinterpretation as ETB, displaying explicit `Excluded (<CODE>)` / `Currency Review` / `(Unverified)` indicators. Strict integer minor-unit decimal parsing eliminates floating-point input math on both platforms.
  - **Canonical `entryType` & `debtStatus` Contract (Finance Stage A):** Both platforms serialize and export canonical `snake_case` `entryType` (`standard`, `transfer`, `debt_issuance`, `settlement`, `split_expense`, `adjustment`, `write_off`) and canonical `snake_case` `debtStatus` (`active`, `settled`, `written_off`, `voided`) aligned with `shared_foundation/schema_contracts.json`. On read/import, both accept documented legacy aliases (`debtIssuance`, `debt_origin` → `debt_issuance`; `splitExpense` → `split_expense`; `writeOff` → `write_off`; `debt_settlement` → `settlement`; `opening_balance`, `opening`, `correction`, `void_reversal` → `adjustment`; `partially_settled` → `active`; `writtenOff` → `written_off`) and fail closed on empty strings `""` or unknown enum values without silent defaulting or store mutation.
  - **Safe Legacy Account Backup/Restore Preservation (Finance Stage A):** Across **all** supported snapshot versions (`schemaVersion: 4..9`, `snapshotFormatVersion: 1..2`), user accounts with valid ISO 4217 non-ETB codes (normalized uppercase, e.g., `'USD'`, `'EUR'`) or empty/omitted `currencyCode` (`""`) survive export, import, backup, and restore alongside linked `transactions`, `journalEntries`, `postings`, and `debts` without currency conversion or silent deletion—while emitting `CURRENCY_UNVERIFIED_ON_LEGACY_IMPORT` diagnostics on Flutter when unverified. System control accounts remain strictly `'ETB'`, and unrecognized non-empty currency codes (e.g., `'XYZ'`, `'BAD123'`) or non-strings fail closed pre-mutation. Web/Node Stage 2.2 + Stage A enforcement is verified via `npm test`; Flutter/Drift execution remains **Unverified** locally pending CI (`flutter analyze` & `flutter test`).

- **Stage 5 & Stage 6 Financial SMS Draft Isolation (No Automatic Posting & Local-Only Raw SMS Privacy):**
  - Imported or pasted CBE, Telebirr, and BOA SMS messages enter staging (`SmsDraftsTable` on Flutter / `daywell_finance_sms_drafts` on Web) strictly as drafts (`needs_review` or `unrecognized`) and **never** create `JournalEntries`, `Postings`, `SimpleTransactions`, or balance/budget/report mutations prior to explicit user approval (`approveSmsDraft` / `FinanceSmsService.approveDraft`).
  - **Stage 6 Android Read-Only SMS Inbox, Daily Scan & Immediate Incoming Broadcast (Implemented in Code / Android CI Pending):** On Android, optional `READ_SMS` powers read-only `Telephony.Sms.Inbox` scanning (`SmsInboxBridge` + `SmsInboxScanWorker` ~24h `WorkManager` periodic scan + foreground startup/resume catch-up) and independent optional `RECEIVE_SMS` powers immediate incoming broadcast detection (`SmsReceivedBroadcastReceiver` + unique one-time `SmsImmediateScanWorker` without altering periodic WorkManager schedules), both reusing Stage 5 `FinanceSmsParsers` and deduplication. Daily/manual/catch-up scans use a bounded 7-day initial lookback or rewind 20 minutes before `device_sms_last_checkpoint_utc`, commit chronologically with one SQLite transaction per message updating draft + monotonic checkpoint together (`PRAGMA busy_timeout = 5000` enabled in `AppDatabase.beforeOpen`), and write `device_sms_last_success_utc` after completion. Immediate `SMS_RECEIVED` tasks serialize via the native scan lock, handle direct broadcast payloads as well as safe inbox-fallback retries (`Result.retry()`) when the SMS has not yet materialized in `Telephony.Sms.Inbox`, intentionally preserve `device_sms_last_checkpoint_utc` and `device_sms_last_success_utc` (`advanceCheckpoint: false`, `recordCompletionSuccess: false`) so missed earlier inbox messages stay discoverable by daily/catch-up scans, and keep all `device_sms_*` `AppSettings` keys excluded from snapshots and backups (`AppSettingsBackupPolicy` `'device_'` prefix).
  - BOA POS authorization locks (`is locked from your account ... Due to POS TRANSACTION`) classify as non-ledger informational notices (`status: 'unrecognized'`, `isNonLedgerNotice: true`) and cannot be approved as expenses.
  - Principal amounts (`principalCents`) and provider fees (`serviceFeeCents`, `vatCents`, `otherChargesCents`) remain separated through approval, posting fee legs to `cat-fees` (`Financial Fees`).
  - `smsDrafts`, `rawSmsText`, and `device_sms_*` metadata are **strictly local-only** and intentionally excluded from `SharedStateBridge` canonical snapshots, Finance-only exports, `.daywell` backups, and `DataPortabilityService` CSV/SQL/XLSX/ZIP exports.

### Calendar & Time Invariants (**Implemented** in Dart & TypeScript)
- **Zone**: Fixed `Africa/Addis_Ababa` (`UTC+3`, `fixedUtcOffsetMinutes: 180`, zero DST).
- **Date-Only vs. Instant**: Civil calendar dates use `YYYY-MM-DD` (`CalendarDate`); timestamps use UTC ISO-8601 (`EthiopiaClock`). Both Projects `startDate`/`targetDate` and tracking record `recordedDate`/`scheduledDate` use canonical `YYYY-MM-DD` rather than UTC-shifted instants, keeping daily outreach totals accurate regardless of Gregorian vs. Ethiopian display formatting.
- **Ethiopian Calendar**: 13 months; 30 days in months 1–12; Pagume 5 days (6 in leap years where `year % 4 == 3`); Julian Day Number anchor `1724221`.

## 6. Backward Compatibility & Versioning Rules ([ADR-007](./decisions/ADR-007-mandatory-backward-compatibility.md))

Daywell strictly separates its version domains so changing one boundary never silently mutates unrelated contracts:

1. **Separated Version Domains:**
   - **Drift Database Schema (`AppDatabase.schemaVersion`):** `13` (`v9 -> v10` adds Stage 0.2B Task fields and `DailyPlanningEntries` table; `v10 -> v11` adds Stage 8 nullable `Notes.linkedModule`/`linkedId` + `idx_notes_linked`; `v11 -> v12` adds Stage B `DailyRhythmDays` table + `idx_daily_rhythm_days_updated_at`; `v12 -> v13` adds Stage 5 local-only `SmsDraftsTable` + indices).
   - **Shared Foundation Contract (`schema_contracts.json`):** `v2.0.0`, `schemaVersion: 13` (tracks SQLite/domain parity).
   - **Canonical Exchange & Seed Version (`canonical_seed_database.json`, `DatabasePersistenceCoordinator.exportSnapshot()`, `SharedFoundationBridge.exportToCanonicalJson`, `SharedStateBridge`):** Emits exchange `schemaVersion: 5` (with `financeSchemaVersion: 7` on Web); Stage F4 Finance-only snapshots reuse these same exchange bounds paired with `financeOnly: true` and `exportScope: 'finance_only'` (and omit local-only SMS drafts).
   - **Canonical Snapshot Format & Source Database Metadata (`snapshotFormatVersion` / `databaseSchemaVersion`):** `DatabasePersistenceCoordinator` and `SharedStateBridge` emit `snapshotFormatVersion: 2` and `databaseSchemaVersion: 13` alongside exchange `schemaVersion: 5` (with `financeSchemaVersion: 7` on Web).
   - **Snapshot Ingest Compatibility Bounds:** Exchange `schemaVersion` accepts `4..9` (omitted => `5`); `snapshotFormatVersion` accepts `1..2` (omitted treated as legacy `1`); optional `databaseSchemaVersion` accepts `1..13` (format-2 accepts previously released `9`, `10`, `11`, and `12` alongside current `13` when specified); values above upper bounds (`databaseSchemaVersion >= 14`) fail closed as `unsupportedFutureSchema` / `unsupported_future_schema` and malformed/non-positive values fail closed as `invalidSnapshotVersion` / `invalid_snapshot_version` before mutation across `DatabasePersistenceCoordinator` (both full and Finance-only snapshot importers), `EncryptionBackupService`, and `SharedStateBridge`.
   - **Encrypted `.daywell` Envelope Format:** Remains `format_version: 1` (`header.schema_version` matches inner exchange `schemaVersion`, emitting `5` on new backups).
   - **Portable `.daywellproject` Package Format ([ADR-010](./decisions/ADR-010-projects-stage3-portable-project-package.md)):** Remains `formatId: "daywell_project_package"`, `formatVersion: 1` (`minSupportedFormatVersion: 1`, `currentFormatVersion: 1`), independent of SQLite `13`, `schema_contracts` `13`, exchange `5`, Finance `7`, and `.daywell` `1`.
   - **Legacy Web `LocalDatabaseState`:** Remains `version: 3` (unchanged).
2. **Preserve Previously Released Migrations & Backups:** Previously released `AppDatabase.onUpgrade` steps (`from < 2` through `from < 13`, verified sequentially ascending in `app_database.dart`) and previously released `.daywell` backup formats (`format_version: 1`) remain supported until retired by an explicit, approved deprecation decision (no arbitrary rolling cutoff). Static AST/token enforcement via `npm run check-migrations` ([`scripts/check_migration_compatibility.mjs`](../../scripts/check_migration_compatibility.mjs) and [`scripts/migration_compatibility_baseline.json`](../../scripts/migration_compatibility_baseline.json)) verifies monotonic `schemaVersion >= 13`, explicit `if (from > to) { throw ...; }` fail-closed guard at the top of `onUpgrade` (and absence of nonexistent Drift `onDowngrade`), preserved ascending `from < 2..13` branches, required delegate classes (`V6LedgerMigrator`, `V7LedgerHardener`), and prohibition of `fallbackToDestructiveMigration` (**runtime SQLite migration execution remains CI/Flutter-only and Unverified locally**).
3. **Forward Database Migration Standards (`v13` Baseline -> `v14+`):**
   - `AppDatabase.schemaVersion => 13` is the current baseline from which all future schema increments (`v14+`) must guarantee non-destructive upgrades and user data preservation.
   - All future `onUpgrade` steps (`from < 14`, ...) must remain incremental (`if (from < N)` in ascending order), deterministic, idempotent when reopened at the target `user_version`, and free of destructive table drops or data resets.
   - Failed migrations must roll back atomically leaving the prior `PRAGMA user_version`, schema, and user rows intact; unsupported future schemas (`from > to`) must fail closed with `UnsupportedDatabaseVersionException` / `DatabaseFailureCategory.unsupportedSchemaVersion` without deleting or overwriting user database files or allowing blind retries.
4. **No Blanket Historical Rewrite:** Existing historical migrations (`from < 2` through `from < 8`) and untouched historical defects are evaluated on touch or when posing material data-integrity or functionality risks rather than through unrequested blanket retroactive rewrites.
